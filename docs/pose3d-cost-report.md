# P0-C：本机资源实测

更新：2026-11-19。已记录两条模型路径的 3 帧探针，以及同一授权视频中 3 个连续研究窗口、每条路径共 183 帧的资源实测。窗口尚未人工确认覆盖完整挥拍；长片段、云端成本及并发测试仍未完成。所有视频在本机处理。

## 连续研究窗口实测（2026-11-19）

来源：`data/pose3d-research/windows-rtmlib-01/report.json` 与 `data/pose3d-research/windows-mmpose-01/report.json`。两条路径在本机 arm64 CPU 上先后独立运行，每次加载一次模型，顺序解码同一个 480×854、448 帧代理视频，只对选定的 183 帧推理。它们复用相同帧的既有 2D bbox，不包含生成原有 2D 结果或额外检测器的成本。选择与评估方法见 [连续窗口研究记录](pose3d-window-research.md)。

总耗时从脚本入口计至最终记账，包含授权、文件 hash、实际代理 PTS 核验、模型加载、完整顺序解码、推理与中间证据写入，**不含最后一次报告写入**，也不是用户端到端等待时间。加载阶段包含对应运行时导入、会话或 checkpoint 初始化及加载器来源记录；两套加载器工作不同。解码计时包含 VideoCapture 创建、全部帧读取、EOF 与释放，排除推理、帧校验和 ffprobe；ffprobe 已纳入总耗时。推理计时包含预处理、模型调用、上游后处理与输出形状校验，失败尝试也应计入；本次没有失败。CPU 时间为进程累计时间，多线程下可大于墙钟耗时。RSS 包含运行时导入等进程生命周期分配，不是模型独占内存。

每个窗口约 2 秒；窗口总耗时从首个选定帧开始读取计至末个选定帧处理并写完中间报告，排除模型加载和窗口之间的解码。三个窗口来自同一视频，不是三段独立拍摄场景，也未标为人工确认的完整挥拍。

A 使用 ONNX Runtime 默认线程设置，B 使用 4 个 PyTorch CPU 线程；模型规格、运行时和加载工作均不同。两者仅各运行一次，未控制系统缓存或其他系统负载，因此以上结果只描述本次处理，不能作为公平性能排序、冷启动基准、稳定 FPS 或产品耗时承诺。此次未测 GPU/VRAM、重试开销或金额；183 帧全部产生 RAW 输出也不表示三维结果准确或发布门槛已通过。

## 历史记录：路径 A 的 3 帧 RGB 探针

来源：`data/pose3d-research/probes/rtmw3d-rgb-clock-02/report.json`。输入是一段 480×854、448 帧代理视频，取第 60、169、327 帧；直接复用同帧既有 2D bbox，不包括检测器成本。模型为固定 RTMW3D-x ONNX，设备为本机 arm64 CPU、`CPUExecutionProvider`。完整权重和环境来源见 [模型实测记录](pose3d-model-evaluation.md)。

| 实测项 | 结果 | 计量边界 |
| --- | ---: | --- |
| 视频取帧 | 0.1011 秒 | 获取指定探针帧 |
| 模型加载 | 0.2466 秒 | 该进程中的加载计时 |
| 第 60 帧推理 | 0.2838 秒 | 包含预处理、ONNX、后处理 |
| 第 169 帧推理 | 0.0709 秒 | 同上 |
| 第 327 帧推理 | 0.0646 秒 | 同上 |
| 探针记录的总耗时 | 1.4423 秒 | 脚本内计时，非端到端用户等待时间 |
| 进程生命周期峰值 RSS | 1,141,030,912 字节 | 约 1.063 GiB；不是模型独占内存 |

这些数据不构成推理 FPS 承诺。首帧与后两帧耗时不同，只测 3 帧不足以建立稳定吞吐分布；帧间间隔也不代表处理了完整窗口。没有独立 VRAM 测量，未由 CPU 数据外推 GPU 性能。数学相机恢复实验不重复运行模型，不能把它的 15 个情景当作 15 次推理。

## 历史记录：路径 B 的 3 帧 MMPose-L CPU 探针

独立环境为 PyTorch 2.2.2 / MMPose 1.3.2 / 本机编译的 MMCV 2.1.0 CPU，4 个 PyTorch 线程。使用与 A 相同代理、帧和 bbox，不运行检测器。环境安装及编译不计入下表的探针耗时，完整记录见 [MMPose 环境说明](pose3d-mmpose-environment.md)。

| 实测项 | 首次 `mmpose-l-01` | 补齐解码配置后重跑 `mmpose-l-02` |
| --- | ---: | ---: |
| 取帧秒数 | 0.1440 | 0.1274 |
| 模型载入阶段秒数 | 14.0956 | 5.5049 |
| 第 60 帧推理秒数 | 0.1087 | 0.0839 |
| 第 169 帧推理秒数 | 0.0727 | 0.0747 |
| 第 327 帧推理秒数 | 0.0702 | 0.0729 |
| 探针记录总耗时秒数 | 15.0504 | 6.3704 |
| 进程峰值 RSS 字节 | 1,018,609,664 | 873,857,024 |

两次均为独立进程；第一次在载入阶段还触发字体缓存。B 的载入计时包含库导入及初始化，A 的 ONNX 会话载入边界不同，不能直接以表中秒数断言哪个 runtime 冷启动更快。模型也分别是 L 与 X，不是同权重后端性能测试。记录来自两个实际报告，不以多次运行中最小数值作为产品承诺。

## 待完成测量

连续研究窗口的完整帧数、逐窗与总耗时及进程内存已有本轮单次记录。选型前仍需补足人工确认的完整挥拍与独立场景，在可比较的资源配置下测量冷/热启动、重复运行分布、显存、失败重试和并发，并覆盖 10 秒/120 fps 与 60 秒片段。当前既有代理为 30 fps，不能伪造为 120 fps 输入。场景和原始采集时钟尚须补足真实授权材料。

部署单价、调用频次、存储保留期和重试率尚未确定，因此单次金额标为 `not_measurable`。得到完整实测后，再用累计设备运行秒数与部署单价计算，并计入冷启动、排队、存储和重试。当前不以少量探针或单次研究窗口实测估算产品定价。
